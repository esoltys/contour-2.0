# Rebooting Contour: Architecture Guidance for a TypeScript Music Composition System

**The path forward is clear**: Build a pattern-based composition system in TypeScript using Vite for hot-reload, Tone.js as the audio foundation, and a hybrid architecture balancing declarative configurations with functional composition. The most successful music-as-code systems—TidalCycles, Sonic Pi, Strudel—converge on similar principles: pattern algebra for expressiveness, immutable transformations for reliability, and musical time abstractions that feel natural to composers. Your fresh start should embrace these battle-tested patterns while avoiding the complexity traps that plague systems attempting to reinvent foundational libraries.

## What went wrong with the original Contour

While the original Contour project documentation at the local WSL filesystem path couldn't be accessed during this research, examining similar projects that needed reboots reveals consistent patterns. **The "reinventing the wheel" problem typically manifests as custom implementations of solved problems**: building parsers from scratch when parser generator libraries exist, creating bespoke Unicode handling instead of leveraging ICU, or developing proprietary music theory libraries when Tonal.js provides comprehensive coverage. These custom components create cascading maintenance burdens—when dependencies update, custom code breaks. Build complexity explodes when multiple platform-specific implementations must be maintained. Technical debt accumulates as non-standard implementations create compatibility issues with ecosystem tools.

The evidence from similar music programming projects shows that **dependency hell and build fragility** cause the most pain. Complex dependency stacks lead to "very long" installation times and version mismatches that break builds unexpectedly. Tight coupling between components means changes ripple unpredictably through the system. Projects attempting to support multiple platforms simultaneously face exponential testing and maintenance costs. Most critically, projects that deviate from standard protocols or common practices discover that their non-standard implementations create compatibility problems that drive users away.

For the Contour reboot, the lesson is straightforward: **leverage existing, mature libraries ruthlessly**. Use Tonal.js for music theory rather than building custom chord parsing. Adopt Tone.js as the audio foundation instead of wrapping Web Audio directly. Choose Vite for build tooling rather than constructing custom bundler configurations. The value you create should be in the composition layer—the patterns, abstractions, and developer experience for expressing musical ideas in code—not in reimplementing fundamental infrastructure.

## How existing music-as-code systems handle composition

The landscape of music programming reveals three dominant architectural philosophies, each with distinct strengths. **Pattern-based systems** like TidalCycles and its TypeScript descendant Strudel treat music as cyclic patterns that can be transformed through algebraic operations. A pattern like `sound("bd sn bd sn").fast(2).every(4, x => x.rev())` expresses a drum pattern that doubles speed and reverses every fourth repetition. This approach excels at electronic music, live coding, and algorithmic composition because patterns compose naturally—you can stack, sequence, and transform them without thinking about low-level timing. The mini-notation syntax `"bd*4 [sn sn] cp hh"` provides remarkable conciseness for rhythmic patterns, essentially a DSL within the language.

**Functional composition systems** like Leipzig (Clojure) and parts of Overtone emphasize treating musical data as immutable structures transformed through pure functions. Notes are simple data maps `{:time 0 :pitch 67 :duration 2}` that flow through transformation pipelines using threading macros: `(->> melody (where :pitch inc) (tempo (bpm 90)))`. This approach shines for composition work where you're building complex structures from smaller pieces, much like functional programming in general. The immutability enables time-travel debugging, easy undo/redo, and hot-reloading without state management headaches.

**Educational/accessible systems** like Sonic Pi prioritize readability and immediate gratification. The API reads almost like English: `4.times do play 60; sleep 0.25 end`. The `live_loop` concept allows named loops that can be hot-reloaded independently: `live_loop :drums do sample :bd_haus; sleep 0.5 end`. This design philosophy makes the system approachable for beginners while still supporting sophisticated work. The block-based effects system `with_fx :reverb, room: 0.8 do ... end` feels intuitive because it mirrors how musicians think about signal chains.

Examining specific API patterns reveals what makes these systems feel natural versus awkward. **Method chaining** appears universally in modern systems because it enables readable, REPL-friendly composition. Strudel's `note("c e g c").off(1/8, x => x.add(12))` chains transformations left-to-right like Unix pipes. **Musical terminology** matters enormously—calling an operation `transpose` instead of `add` or `retrograde` instead of `reverse` signals that the system understands music, not just data. **Visual rhythm** in code structure helps too; TidalCycles users format their patterns to look rhythmic: `stack [ sound "bd ~ bd ~", sound "~ sn ~ sn" ]`.

The balance between declarative and functional styles varies by system goals. TidalCycles leans heavily functional with pure pattern transformations. Sonic Pi blends declarative parameter configuration with imperative control flow. Tone.js uses object-oriented construction with declarative signal routing. The most successful approach for a TypeScript system appears to be **hybrid**: JSON-serializable configurations for instruments and presets (like React props), but functional composition for musical transformations and patterns (like React components). This gives you the best of both worlds—shareable configs and powerful programmatic composition.

Where systems struggle reveals what to avoid. SuperCollider and Csound suffer from **steep learning curves** due to custom syntax and heavy theoretical prerequisites. Alda's limitation is that algorithmic composition requires wrapping the DSL in another language. Pure markup approaches like Alda lack the compositional power that programming constructs provide. Systems that hide too much abstraction become inflexible when users need fine control. The solution is **layered abstraction**: provide high-level convenience functions, but always allow users to drop down to Tone.js primitives when needed.

## Public domain compositions that prove your system works

**Bach's Invention No. 1 in C Major (BWV 772) stands as the ideal acceptance test** for a music composition system. This 54-second piece demonstrates everything critical: two independent voices working simultaneously, imitative counterpoint where one voice echoes the other with precise timing, consistent rhythmic motion in sixteenth notes, clear harmonic progressions, and well-defined melodic construction. The piece is intermediate difficulty—achievable but not trivial. It's universally recognizable, frequently taught, and available in multiple editions on IMSLP including MIDI references. Most importantly, it surfaces the right challenges: Can your system maintain voice independence? Does it handle imitative entries correctly? Can it keep two melodic lines coherent when they cross? This piece will immediately expose weaknesses in multi-voice handling, timing precision, and voice-leading implementation.

**Bach's Invention No. 4 in D Minor (BWV 775) serves as an excellent secondary target**, slightly easier than No. 1 but introducing new challenges. Built around descending D harmonic minor scales, this 64-second work tests minor key handling with accidentals, scalar passages in both hands, and the emotional expressiveness of the minor mode. It's considered one of the easiest Bach Inventions, making it ideal for early testing when the system is still maturing. The characteristic descending sevenths test dramatic interval jumps, while the minor harmony requires proper handling of raised leading tones (C# in D minor).

For **stylistic variety beyond Baroque counterpoint**, Scott Joplin's "The Entertainer" demonstrates different capabilities entirely. The ragtime syncopation—right hand playing off-beat against a steady left hand—tests whether your timing system can handle displaced accents accurately. The stride piano bass pattern with octave jumps tests note placement precision. The clear A-B-A-C-D structure demonstrates phrase organization and repeat handling. You can use just section A (about 45 seconds) for focused testing rather than the full 3.5-minute piece. This proves the system isn't limited to European classical music and can handle American vernacular styles. The piece is iconic—everyone knows it from "The Sting"—providing instant recognizability for validation.

**Chopin's Prelude in E Minor (Op. 28, No. 4)** tests a completely different texture: melody over chordal accompaniment rather than independent voices. At only 16 bars and approximately 2 minutes, it's practically sized. The piece tests sustained notes in melody while accompaniment continues, subtle dynamic shading (pp to p with gentle crescendos), chromatic harmony with sophisticated voice leading, and pedaling indications. It's technically straightforward but requires nuanced dynamic control. This piece validates that your system can handle homophonic texture, not just polyphonic counterpoint, and that it can express romantic-era harmonic complexity.

For **simplicity or pedagogical purposes**, a polyphonic arrangement of "Greensleeves" offers flexibility. The traditional melody in 6/8 compound meter with modal harmony (Dorian mode) can be arranged with 2-3 voices depending on complexity needs. At roughly 30 seconds for one verse, it's extremely manageable. It demonstrates modal music outside major/minor systems, compound meter handling, folk ornamentation with grace notes, and system versatility across genres. You can scale this piece's difficulty by choosing or creating arrangements of varying complexity.

**Why Moonlight Sonata failed** reveals what to avoid. The famous first movement is deceptively simple—primarily repeating triplet arpeggios over simple bass—so it doesn't demonstrate sufficient rhythmic variety or clear voice independence. It's atmospheric rather than structurally demonstrative. The third movement swings too far the other direction: Grade 8 difficulty with rapid arpeggios and octaves that would overwhelm acceptance testing. The piece requires subtle emotional interpretation that's difficult to codify, and at significant length, it's impractical for iterative testing. Most critically, **the voices aren't clearly independent** like in contrapuntal music, making it harder to verify multi-voice implementation correctness. Choose pieces where success is objectively verifiable.

## Supporting multiple notation systems without architectural collapse

The evidence across music programming systems proves that **supporting multiple notation types is absolutely feasible with proper architecture**. VexFlow and AlphaTab successfully render standard notation and guitar tablature simultaneously. TablEdit imports eight formats and exports three. Tonal.js provides pure music theory abstraction that works with any notation as input or output. JFugue maintains a single internal model while exporting to MIDI, MusicXML, ABC, and LilyPond. These existence proofs demonstrate that the challenge isn't technical impossibility but architectural discipline.

**The abstraction layer approach emerges as the clear winner**. Structure your system with input parsers feeding a unified internal model, which output renderers then transform to various formats. The parsers convert from ABC notation, chord symbols, tablature, Nashville numbers, and programmatic patterns into a canonical representation. The internal model represents musical concepts like notes (pitch, duration, articulation), chords (root, intervals, voicing), rhythm (time signatures, tempo, beat positions), structure (measures, sections, repeats), and metadata. Output renderers then transform this model to standard notation, guitar tablature, chord charts, MIDI files, audio, and lead sheets. This architecture requires N converters instead of N² direct conversions between formats, provides a single source of truth, allows incremental addition of notation types, and keeps composition logic notation-agnostic.

Looking at specific notation types reveals both opportunities and challenges. **Traditional Western notation** expresses pitch (note names with accidentals), duration (whole/half/quarter/eighth notes), articulation (staccato, accent, legato), and dynamics. Systems like Semitone handle this comprehensively with constructs like `qc` (quarter note C), `hd#` (half note D sharp), and `w.g` (dotted whole note G). **Guitar tablature** expresses fret positions and string numbers, implying pitch but allowing multiple fingerings for the same note. VexFlow's VexTab notation `tabstave notation=true; notes :q 4/5 5/4 6/3 7/2` demonstrates combined rendering. **Jazz chord symbols** like C13♭9 or Dm7♭5 express harmonic function with extensions and alterations. Tonal.js successfully parses these: `Chord.get("C13b9").notes` returns the full voicing. **Nashville number system** provides key-independent notation where 1-4-5-1 means I-IV-V-I in any key, requiring scale degree calculation. **Programmatic patterns** generate notes algorithmically rather than specifying fixed values.

The "impedance mismatch" between notation systems creates inherent conversion challenges. Tablature to staff notation involves multiple possible note spellings (G# versus Ab). Chord symbols to specific notes involves ambiguous voicing choices (how to voice Cmaj7?). Standard notation to tablature involves multiple possible fret positions for the same pitch. These conversions can't all be lossless. The solution is **implementing lossless core conversions plus lossy adapters**: MIDI number to note name is lossless, chord symbol to voicing is lossy and requires default voicing heuristics, standard notation to tablature is lossy and may need user disambiguation.

Your core data structures should separate what's certain from what's interpreted. A note representation might include `pitch: 60` (MIDI number, unambiguous), `pitchClass: "C"` (note name, for display), `duration: 0.25` (fractional beat), and optionally `position: { string: 1, fret: 5 }` for tablature-specific information. A chord representation needs `root: "C"`, `quality: "maj7"`, `extensions: ["9"]`, `alterations: ["b9"]`, `bass: "E"` (for slash chords), and optionally `voicing: [60,64,67,71]` when specific voicing matters. This structure allows different notation parsers to populate the fields they understand while leaving others undefined.

**Warning signs from failed approaches** guide what to avoid. Don't tightly couple notation to rendering—this makes supporting multiple notations impossible. Don't use strings for everything; Tone.js's limitation of requiring note arrays like `["C4", "E4", "G4"]` with no built-in chord parsing forces users to external libraries. Don't parse with regex; even Semitone's author admits "code quality is pretty bad" and wants to convert to parser combinators. Don't try supporting everything simultaneously; MusicXML's 300-page specification is verbose and has multiple ways to encode the same information. Don't lack a clear internal model; ABC notation suffers from inconsistent interpretation across implementations.

For practical implementation, **start with 2-3 notation types and expand**. Begin with traditional notation (most universal), chord symbols (common in jazz/pop), and programmatic patterns (your differentiator). Add tablature later if users request it. Use existing libraries ruthlessly: Tonal.js for music theory, VexFlow for rendering standard notation, existing MIDI libraries rather than building from scratch. Make format conversion explicit rather than automatic—let users trigger format changes and show what information might be lost. Provide sensible defaults for ambiguous conversions but allow overrides. Consider that read versus write capabilities can differ; parsing more formats than you generate is acceptable, and display-only adapters are simpler than full editing support.

## Critical architecture and design decisions before coding

**The build tool choice dramatically impacts development experience**, and the research unequivocally favors Vite. Vite achieves sub-second dev startup using esbuild for pre-bundling, instant HMR through native ESM without full rebuilds, and per-module hot updates reflecting changes in under 100ms. TypeScript support is built-in, configuration complexity is low, and the Rollup plugin ecosystem is rich. In comparison, webpack suffers from 5-30 second startup times, 1-5 second HMR cycles, high configuration complexity, and the need for separate ts-loader configuration. Esbuild offers similar speed to Vite but requires DIY implementation of HMR and plugin systems. For music development specifically, Vite's instant feedback loop makes the compositional process feel live and interactive—critical for creative work.

However, **standard hot-reload will cause audio glitches** if implemented naively. Audio suddenly stopping creates clicks and pops. The solution requires custom Vite plugin handling:

```typescript
// Custom music-aware HMR
{
  name: 'music-hmr',
  handleHotUpdate({ file, server }) {
    if (file.endsWith('.music.ts')) {
      server.ws.send({
        type: 'custom',
        event: 'music-reload',
        data: { file }
      })
    }
  }
}
```

The client side handles this gracefully by fading out audio over 300ms, stopping the Transport cleanly, then accepting the module update. This transforms hot-reload from jarring to seamless.

**Type system design for musical concepts prevents entire bug categories**. Using plain `number` for all time, frequency, and velocity values allows nonsensical operations like adding beats to hertz. Branded types solve this:

```typescript
type Hz = number & { __brand: 'Hz' }
type BPM = number & { __brand: 'BPM' }
type Seconds = number & { __brand: 'Seconds' }

const freq: Hz = 440 as Hz
const tempo: BPM = 120 as BPM
// freq + tempo // Type error!
```

Template literal types provide compile-time validation of note names:

```typescript
type NoteName = `${NoteLetter}${Accidental}${Octave}`
type NoteLetter = 'C' | 'D' | 'E' | 'F' | 'G' | 'A' | 'B'
type Accidental = '' | '#' | 'b'

const note: NoteName = 'C#4' // Valid
const bad: NoteName = 'H5'   // Type error
```

This gives you IntelliSense autocomplete for musical values and catches errors at compile time rather than runtime. Immutable data structures enforced through TypeScript's `readonly` prevent accidental mutations that cause hot-reload and debugging nightmares.

**The relationship between Tone.js and your composition layer requires careful layering**. A four-level architecture prevents both over-abstraction and under-abstraction. Layer 1 consists of direct Tone.js primitives—Synth, Transport, Signal, Effects—unchanged. Layer 2 wraps these in musical primitives, thin adapters that handle note scheduling and effect chaining with musical terminology. Layer 3 provides composition abstractions: Voice, Pattern, and Sequence classes that enable functional composition. Layer 4 delivers the DSL syntax users interact with: `track()`, `sequence()`, `parallel()` functions that read naturally. Critically, **never hide Tone.js completely**—users should be able to drop to any layer when they need fine control.

**Plugin architecture for different renderers demands type-safe design**. Define a `RendererPlugin<TConfig>` interface with `initialize`, `render`, and `shutdown` methods. Implement a plugin registry with dependency validation so plugins can declare dependencies on other plugins, and load order is resolved automatically. This architecture supports diverse renderers: audio exports to MP3/WAV/OGG using Tone.Offline plus encoders, MIDI exports to Standard MIDI File and MusicXML formats, visualizers rendering to Canvas/WebGL or video via FFmpeg, and data exports producing JSON events or musical analysis. The type parameter `TConfig` allows each plugin to specify its configuration schema, maintaining type safety throughout.

**Testing strategies for music code span multiple levels** because different aspects require different validation. Unit tests verify pure functions like transpose, retrograde, and chord construction—standard Jest or Vitest tests. Snapshot tests capture event structure to detect unintended changes in pattern generation. Golden file tests compare rendered audio against reference files using audio buffer similarity metrics, allowing 99.9% similarity with small tolerance for floating-point differences. Property-based tests using fast-check verify algebraic properties like `retrograde(retrograde(x)) = x`. Integration tests validate Tone.js scheduling and Transport interaction. This multi-level approach catches bugs from music theory errors to timing precision issues.

**Version control for audio output follows a clear principle: track code only, not binary artifacts**. Ignore all rendered audio files (WAV, MP3, OGG) in `.gitignore` since they're deterministic build artifacts from source code. Track manifest files that document what was rendered, including SHA-256 hashes of source, render timestamp, duration, and format. For reference files needed in golden file tests, use Git LFS to avoid bloating the main repository. This approach keeps clones fast, diffs meaningful, and the repository focused on source material. Audio regenerates from code just like compiling C++ binaries from source.

**Timing and synchronization require functional reactive programming concepts**. Model time as a first-class value with types like `Behavior<T> = (time: Seconds) => T` for continuous time-varying values and `Event<T>` for discrete occurrences. Implement tempo curves as behaviors: `TempoCurve = Behavior<BPM>` allows accelerando and ritardando expressed as functions over time. Quantization to musical boundaries prevents rhythmic drift: `Tone.Transport.nextSubdivision('1m')` ensures loops start on bar boundaries. Swing and groove become functional timing modifiers: `swing(amount)` shifts off-beats by a percentage. Look-ahead scheduling with 0.1-second buffers prevents audio glitches from JavaScript timing imprecision. This functional approach to time makes temporal reasoning explicit and composable.

**Common pitfalls must be avoided from the start**. Never use `setTimeout` or `setInterval` for audio scheduling—they have 10-20ms jitter that ruins musical timing. Always use Tone.Transport and AudioContext time. Don't start audio before user interaction; browsers require user gestures before playing audio, so wait for a button click then call `Tone.start()`. Don't create Tone.js synths and effects in loops without disposal—AudioNodes leak memory if not explicitly disposed. Don't commit binary audio files to Git; repository size explodes and clones become painfully slow. Don't mix units without type safety; seconds plus beats equals confusion and bugs. These issues cause subtle problems that become deeply embedded if not addressed architecturally from day one.

## Unresolved questions requiring prototyping

Several architectural decisions need practical exploration before committing. **Hot-reload edge cases** need testing: Should reload pause or restart from beginning when occurring mid-playback? Can Transport position be maintained across reloads for seamless continuation? How do you handle multiple rapid reloads without audio queue buildup? **Plugin sandboxing** raises security questions: Should plugins run in separate contexts? Do you need Web Workers for isolation? How do you prevent malicious plugins from accessing the main audio graph? **Collaborative editing** for multi-user composition isn't addressed: Can operational transforms merge concurrent musical edits? Would CRDTs work for music data structures? How do you visualize remote user cursors in musical time?

**Performance at scale** needs empirical testing: How many simultaneous voices before glitches occur? Should rendering offload to Web Workers? Would WASM implementations of DSP-heavy operations provide meaningful speedup? **MIDI input/output integration** requires exploration: How do you type MIDI messages in TypeScript? Can you sync MIDI clock with external devices? What's the latency path for real-time MIDI input integration? **Mobile and browser compatibility** needs validation: What are iOS Safari's specific AudioContext restrictions? How much do timing differences vary across browsers? Do you need fallbacks for older browsers?

These questions can't be answered through research alone—they require building prototypes, measuring performance, and making empirical tradeoffs. Budget time for experimentation before locking in these design decisions.

## Recommendations: What to do now

**Start with Vite, TypeScript 5.3+, and Tone.js 14.8+ as your foundation**. Add Tonal.js for music theory utilities rather than building chord parsing from scratch. Implement branded types for Hz, BPM, Seconds, and MIDI note numbers immediately—this prevents unit mixing bugs that become deeply embedded. Design your four-layer architecture with clear boundaries: Tone.js primitives untouched at the bottom, thin musical wrappers above, composition abstractions in the middle, and DSL syntax at the top.

**Adopt the hybrid declarative-functional pattern** explicitly inspired by React. Use JSON-serializable configurations for instrument presets, effect settings, and static definitions. Use functional composition with pipe, map, transpose, and retrograde for dynamic musical transformations. This combination gives you shareable configs alongside powerful programmatic composition, satisfying both the casual user wanting presets and the power user needing algorithmic control.

**Implement pattern algebra from day one**, drawing on TidalCycles and Strudel's proven designs. Create a Pattern class with `fast`, `slow`, `rev`, and `every` transformation methods. Consider adding mini-notation parsing for rhythm strings like `"bd*4 [sn sn] cp hh"` as syntactic sugar, though this can come later. Patterns should be immutable data structures that return new instances from transformations, enabling undo, hot-reload without state corruption, and time-travel debugging.

**Build the plugin system early**, not as an afterthought. Define the `RendererPlugin` interface with explicit dependency declaration and validation. Implement MP3 and MIDI renderers first since they have clear success criteria. Add visualizers later when the core is solid. This extensible architecture prevents painting yourself into corners where new output formats require refactoring core systems.

**Test at multiple levels from the beginning**. Write unit tests for music theory functions—transpose, chord construction, scale generation. Add snapshot tests for event structures as you implement pattern transformations. Create golden file tests once you have basic rendering, starting with simple melodies before complex polyphony. Don't test subjective qualities like "does it sound good?"—test objective properties like "does this chord contain the correct notes?" and "does this rhythm match the expected event times?"

**Use Bach Invention No. 4 in D Minor as your first acceptance test** since it's slightly easier than No. 1 while still demonstrating multi-voice counterpoint, minor key handling, and melodic construction. Progress to Invention No. 1 in C Major once the basics work. Add Scott Joplin's "The Entertainer" (section A only) to prove stylistic versatility. These three pieces comprehensively validate that your system handles the fundamentals correctly.

For the original Contour project specifically, **if you can access those local docs**, extract explicit lessons about what wheels were reinvented—custom parsers, music theory libraries, or synthesis wrappers—and commit to using existing solutions instead. Document the specific pain points around dependencies, build complexity, or architecture that necessitated the reboot. These historical lessons prevent repeating the same mistakes in different forms.

**Focus ruthlessly on the composition layer as your unique value**. Don't rebuild Tone.js, don't reimplement Tonal.js, don't create a new bundler. Your differentiation comes from the patterns, abstractions, and developer experience you create for expressing musical ideas in TypeScript. Make simple things simple—`play("C4")` should work—but complex things possible through compositional power. The Unix philosophy applies: small, focused, composable pieces that do one thing well and chain together naturally.

The path forward is clear, the pitfalls are documented, and the architectural patterns are proven. Build methodically, test continuously, and ship iteratively. Your music composition system stands on the shoulders of giants—Tone.js for audio, Tonal.js for theory, Vite for tooling, TidalCycles for patterns. Create the layer that makes musical expression in TypeScript feel natural, powerful, and joyful.
